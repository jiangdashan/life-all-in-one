## v61 封面小字清晰度修复（已上线 /43/）

### 现象与根因
- 用户回传鸿蒙手机截图：封面墙 2 列布局下，标题「成何体统」等**粗到笔画粘连**，底部类型小字（剧/电影）**糊成一个色块**。

- 数学复核：封面墙单卡 ~150px 宽 / viewBox 90 宽 = 1.7 倍缩放，标题 10px → 显示 16.7px 本应清晰 ⇒ **字重才是主因，不是字号**。

### 修改（`_tools/_apply_v61.py` + `_apply_v61b.py`）
- svg 根加 `text-rendering="geometricPrecision"`。
- 标题：`font-weight 700→500`、`font-size 10→9.5`、行距 `12→11.5`、起始 `y 78→76`、字体栈补 `HarmonyOS Sans SC`/`MiSans`。
- 类型小字：`font-size 7→9`、`opacity .85→.7`、`y 112→113`。
- 首字水印：`40→34`、`opacity .3→.22`、`font-weight 700→400`（宋体合成加粗同样会糊）；mini 模式 `46→44 / .32→.24`。

### 踩坑
- **JS 单引号字符串内不能再嵌单引号**：拼 CSS 字体栈时写成 `font-family="...'PingFang SC','HarmonyOS Sans SC'..."`，直接截断 JS 字符串 → `node --check` 报 `Unexpected identifier 'PingFang'`。CSS font-family 里带空格的字体名**不加引号也能被浏览器正确解析**（标识符序列），去掉引号即可。

## v63 多用户数据隔离可行性调研（仅调研，**未改代码**）

用户诉求：让另一个人也能用这个工作台，对方看到的是完全空数据，且双方数据不互串。明确要求先只做可行性讨论。

### 现状核查结论（读码确认，非推测）
- **好消息：云端已经是多用户架构**，无需重构数据模型。
  - `authUserId(pw) = SHA256('richangji-v32-uid-2026-09' + ':' + pw)` → userId；
  - `dbAdd` 自动注入 `userId`（信封 `{text:uid}`）；`dbFetchAll` 末尾 `all.filter(_authGetRowUserId(r)===uid)`，**未登录返回 null 不是 []**；
  - 设置同步 `readMetaValue` 走 `dbFetchAll` → **已按 userId 隔离**；
  - `clearAllRemoteTables` 基于 `dbFetchAll` 拿 id 再删 → 不会误删他人。
- **必须补的 3 个洞（否则会互串）**：
  1. **登录入口拦人**：`cloudCollectUserIds` 只要探测到云端已有 userId，就置 `cloudVerify=true` → 走「必须与原密码一致」分支，**对方设自己的密码会被判"密码不正确"**。这是第二个用户根本无法自助建号的硬阻塞（@231600 附近）。
  2. **清空信号是全局的**：`readMetaClearAt` / `readPeriodClearMarker` 用 **`dbFetchAllRaw`**（不过滤 userId）+ 取**全局最大时间戳** → A 点「清空全部」，B 的设备读到该标记会执行 `applyRemoteClear` 把 B 的数据一起清掉。**这是最危险的一处**。
  3. **本地缓存单键**：`STORAGE_KEY` 是全 state 单一键、不含 userId；`AUTH_STORAGE_KEY` 也只存单个 passwordHash。同一浏览器/同一手机先后登两个人 → 本地 state 混在一个对象里，`syncPendingRecords` 会把上一个人无 remoteId 的记录连同**当前 userId 一起推到云端** → 上一个人的数据被"认领"到新用户名下。

### 提出的两条路线（待用户选型）
- **路线 A 物理双开**：源码保持一份，把 14 个 `DB_*` 常量 + `_deploy.py` 的 `DB_IDS`/`NODE_ID` 做成构建参数；新建第二套 14 张表 + 新活页节点 → 独立 URL。隔离性 100%，**完全不触碰认证/同步铁律区**；代价是每加一人多一套表、多一次部署。
- **路线 B 原生多用户**：补上面 3 个洞 + 本地 key 分桶（`STORAGE_KEY` 加 uid 前缀、`AUTH_STORAGE_KEY` 改成 map）+ 切换用户时清空内存 state/index。一次投入可任意加人，但要动全项目风险最高的认证与存储核心。

### 附带提醒
- 另一人的数据仍落在**用户的资料库账号**下（物理托管），只是前端按 userId 隔离；
- 两个用户共用同一批云端表时，**读写量翻倍可能更容易触发 50001 限流**。

## v65 调研：每日自动备份 + 误清空恢复（用户要求「先讨论可行性」，未动代码）

### 关键事实（读代码 + 线上只读核查）
- **清空链路**：`handleClearAll` → 本地 `state.records / mediaItems / habits.entries / weeklyPlan` 全清 + `state.lastClearedAt` → 写 meta 墓碑 `writeMetaClearAt` → `clearAllRemoteTables` 删 **13 张业务表**（DB_LIST 里**不含 DB_META**）→ 再写一次墓碑。

- **致命坑 1 · 墓碑反噬**：`applyRemoteClear(clearAt)` 按 `createdAt > clearAt` 过滤，`readMetaClearAt` 跨设备生效。恢复备份若不**同时撤销本地 state.lastClearedAt + 云端 meta lastClearedAt**，恢复出来的老记录 createdAt 早于墓碑 → 一刷新又被过滤掉、其它设备还会再清一遍。**这是多数恢复方案失效的根因。**
- **致命坑 2 · 恢复不能用覆盖**：用户铁律是 LWW、禁止远程无条件替换本地。恢复必须是「按 id 把快照里缺的记录补回来」的 merge 语义，不能整份覆盖。
- **容量未知**：meta 三列全是 text，SDK 无长度声明；生产环境实测**已成功写入过的最大值 2399 字符**（appSettings）。全量快照估计 100–150 KB（13 张业务表 843 行、CSV 61.7 KB；含 meta 共 863 行 / 91.6 KB）。**能否单行存下必须探针才知道**，否则走分片（每片 ≤2000 字符）→ 属于「要不要写生产表」的取舍，已交用户定夺。
- **没有现成导出/导入实现**：i18n 里有「备份已导出 / 备份导入成功 / 导入备份」等文案，但源码里**不存在任何导出导入函数**（全是历史遗留文案）。不过 `normalizeState()` 已是完整校验器（抛「备份格式不正确」「备份中有损坏的记录」），可直接复用做恢复时的格式校验。
- **触发时机**：纯前端无后台，真「定时」做不到；可行的是「打开 + cloud 同步成功后，当天尚无快照才生成」。用 WorkBuddy 桌面自动化驱动浏览器不可靠（需本机常开）。

- C 双份（推荐）+ 7 / 14 / 30 天滚动保留。

### 容量探针结论（用户授权：`_probe_capacity.py` / `_probe_capacity2.py`，写完按 _id 精确删除）
- **单格 text 字段 ≥ 150KB 完全没问题**：写入 149977 字符（含中文、`¥`、引号、换行）→ 读回**字节完全一致**；400000 字符那条也 `success: true`。
- 所以**不用分片**，一天一行即可。30 天 × 约 150KB ≈ 4.5MB 云端占用。
- 清理已验证彻底：meta 表回到 20 行、探针残留 0、键只剩 appSettings/habitsDef/lastClearedAt/periodClearedAt。
- **坑：Python csv 默认 field limit 131072**，读大字段会 `_csv.Error` 崩；必须 `csv.field_size_limit(10**9)`。第一版探针因此崩在 finally 的读取里，**删除逻辑没跑到**（4 行探针残留在生产表里，事后手工按 add 返回的 id 精确删除才清干净）。→ **探针脚本的删除必须只依赖 add 返回的 id，绝不能依赖读表。**
- **probe 脚本调用姿势**：`acquire_token()` 读 stdin 首行、`_read_input()` 再 read() 剩余 → token 和 records JSON 拼在同一份 stdin：`TOK + '\n' + json_body`；`records` 元素直接是 properties map（不用再包一层 `properties`）；add 返回 `{"results":[{"index":0,"id":...,"success":true}]}`（顶层是 results，不在 data 里）。

### 本地配额是新的硬约束（推翻「本地也留 30 天」）
- media 的 `cover` 可以是 **base64 dataURL**（`readAsDataURL` + `canvas.toDataURL('image/jpeg',.72)` 本地压缩后存进 state），且 `pushMedia` 明确**只同步 http 链接、不同步本地上传图**。
- 因此本机 state 里可能藏着若干张几十 KB 的封面图，快照体积远不止 150KB。
- 浏览器 localStorage 一般 5MB 上限 → **本机留 30 份大概率撑爆**，且挤出时可能影响主状态写入（现有代码已有「存不下了，请先导出备份」的兜底文案）。
- 建议改为：**本机按总体积自适应滚动**（软上限约 2MB，超了删最老），云端固定滚动 30 天。此点需用户拍板。

3. **云端滚动 30 天**：meta 表单行 `backup:<date>`，单格已验证可存 150KB+。

6. **恢复语义**：先看预览（能找回几条）→ 按 id **合并**、只补缺失，**不覆盖**本地已有、**不碰 settings**（避免回滚主题/开关/PIN）。
